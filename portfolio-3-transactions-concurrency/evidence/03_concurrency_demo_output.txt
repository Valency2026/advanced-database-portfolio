DEMO 1: LOST UPDATE (naive read-then-write)
==============================================================================
Account 30 starts at 10,000. Session A withdraws 3,000, Session B withdraws 4,000.
Correct final balance: 3,000.

[    14.0 ms] Session A BEGIN
[    14.9 ms] Session A read balance = 10000.00
[    65.2 ms] Session B BEGIN
[    66.4 ms] Session B read balance = 10000.00
[   267.9 ms] Session B UPDATE balance = 10000.00 - 4000 = 6000.00
[   269.9 ms] Session B COMMIT
[   269.9 ms] Session A UPDATE balance = 10000.00 - 3000 = 7000.00
[   270.8 ms] Session A COMMIT

Final balance: 7000.00  ->  WRONG - a withdrawal was LOST (3000.00 deducted instead of 7,000)

DEMO 3: ISOLATION LEVEL READ COMMITTED
==============================================================================
Session A reads account 40 twice inside one transaction.
Between the two reads, Session B deposits 1,000 and commits.

[   713.1 ms] Session A BEGIN (READ COMMITTED); first read  = 5000.00
[   717.5 ms] Session B deposited 1,000 and COMMITTED
[   717.7 ms] Session A second read = 6000.00

-> Value changed from 5000.00 to 6000.00 inside one transaction: a NON-REPEATABLE READ,
   which READ COMMITTED allows. Fine for a dashboard, dangerous for a balance check.

==============================================================================
DEMO 3: ISOLATION LEVEL REPEATABLE READ
==============================================================================
Session A reads account 40 twice inside one transaction.
Between the two reads, Session B deposits 1,000 and commits.

[   727.0 ms] Session A BEGIN (REPEATABLE READ); first read  = 5000.00
[   731.4 ms] Session B deposited 1,000 and COMMITTED
[   731.6 ms] Session A second read = 5000.00

-> Same value both times: REPEATABLE READ gives a consistent snapshot (no non-repeatable read).
